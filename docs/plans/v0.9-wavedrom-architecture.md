# v0.9 WaveDrom Architecture

This document defines the implementation shape for WaveDrom support in v0.9.0.

References:

- WaveDrom GitHub: https://github.com/wavedrom/wavedrom
- WaveDrom npm: https://www.npmjs.com/package/wavedrom

## Goals

- Render WaveDrom timing diagrams from Markdown fenced blocks in Preview and PDF.
- Preserve Markdown Studio's local-first policy.
- Keep third-party usage explicit and auditable.
- Reuse the existing diagram container, error, zoom/pan, Preview runtime, and corpus tooling.

## Non-Goals

- Do not call `svg.wavedrom.com`.
- Do not load WaveDrom from a CDN.
- Do not support raw HTML `<script type="WaveDrom">` blocks in v0.9.
- Do not add a WaveDrom editor UI.
- Do not add VCD waveform viewing.
- Do not add remote WaveJSON fetching.

## Third-Party And Local-First Policy

Use the npm package `wavedrom` pinned through `package-lock.json`.

Expected third-party treatment:

- Add `wavedrom` as a direct dependency.
- Bundle WaveDrom into `dist/preview.js` through the existing esbuild flow.
- Document WaveDrom in `docs/third-party-notices.md`.
- Mention MIT license and upstream homepage/repository.
- Avoid vendoring binaries under `third_party/`.
- Avoid all runtime network calls.

This keeps the runtime model aligned with Mermaid:

- The extension ships the renderer.
- Rendering happens locally.
- The webview only executes extension-bundled JavaScript.
- User-authored diagram source is never sent to a remote service.

## Recommended Rendering Path

Use webview-side rendering for v0.9.

Reasoning:

- WaveDrom's documented usage is browser-oriented: JavaScript + skin + SVG output.
- The existing Preview runtime already handles browser-side Mermaid rendering.
- PDF export already injects the Preview runtime and waits for client-side diagrams.
- This avoids adding DOM shims or a second renderer runtime in the extension host.

Extension-host responsibility:

- Detect WaveDrom fenced blocks.
- Replace them with encoded placeholders.
- Keep source-line padding stable.
- Return structured render errors only for extension-host failures.

Webview responsibility:

- Decode WaveDrom source.
- Invoke the bundled WaveDrom renderer with the bundled/default skin.
- Insert generated SVG into `.wavedrom-host`.
- Render visible inline `.ms-error` output on failures.
- Mark each host as rendered/error for PDF readiness.

## Markdown Syntax

Support fenced blocks only:

````markdown
```wavedrom
{ signal: [
  { name: "clk", wave: "p......" },
  { name: "bus", wave: "x.34.5x", data: "head body tail" }
]}
```
````

Fence aliases:

- `wavedrom`
- `wavejson`
- `wavedrom-json`

Do not interpret raw HTML `<script type="WaveDrom">` in v0.9. Markdown Studio should leave raw HTML behavior to the existing Markdown renderer instead of adding a second HTML execution path.

## Pipeline Changes

### Parser

Files:

- `src/types/models.ts`
- `src/parser/scanFencedBlocks.ts`

Changes:

- Add `wavedrom` to `FencedBlockKind`.
- Treat `wavedrom`, `wavejson`, and `wavedrom-json` as WaveDrom blocks.
- Normalize aliases to `wavedrom` internally.

### Renderer

Files:

- `src/renderers/renderWaveDrom.ts`
- `src/renderers/renderMarkdown.ts`

Changes:

- Add `renderWaveDromPlaceholder(source)`.
- Store encoded source as `data-wavedrom-src`.
- Emit:

```html
<div class="diagram-container">
  <div class="wavedrom-host" data-wavedrom-src="..."></div>
</div>
```

### Preview Runtime

Files:

- `media/preview.js`
- `media/preview.css`

Changes:

- Import/bundle WaveDrom and its default skin locally.
- Add `renderWaveDromBlocks()`.
- Run WaveDrom rendering during initial load and `update-body`.
- In PDF/eager mode, render all WaveDrom hosts before export.
- In Preview mode, render eagerly at first. Add visible-first rendering only if benchmarks show a need.
- Cache rendered SVG by source.
- Add readable error output:

```html
<div class="ms-error">
  <div class="ms-error-title">WaveDrom render error</div>
  <pre>...</pre>
</div>
```

Style choice:

- Keep WaveDrom SVG colors as generated.
- Use a light surface for WaveDrom diagrams in dark mode if needed, because timing diagrams usually assume black-on-white readability.

### PDF Export

Files:

- `src/export/exportPdf.ts`

Changes:

- Extend the diagram readiness wait to include `.wavedrom-host[data-wavedrom-src]`.
- A WaveDrom host is ready when it contains an `svg` or `.ms-error`.
- Keep PDF export local; no remote image rendering.

### Zoom/Pan

Files:

- `media/preview.js`

Changes:

- Ensure `.diagram-container` receives zoom toolbar for rendered WaveDrom SVG.
- Use CSS transform fallback for v0.9.
- Do not add high-resolution WaveDrom rerender on zoom unless the baseline output is visibly poor.

## Security Notes

- WaveDrom source is local user-authored Markdown content.
- Source is stored in a data attribute with `encodeURIComponent`.
- The webview CSP remains locked to extension resources.
- No external image/script/network source is needed.
- If WaveDrom internally uses eval-like parsing, it runs in the same local webview trust model already required by Mermaid's `unsafe-eval`.
- Do not support raw WaveDrom script tags in v0.9 to avoid expanding the HTML execution surface.

## Testing Strategy

### Unit

- Fence aliases are detected and normalized.
- WaveDrom placeholders encode/decode source safely.
- Full Markdown render replaces WaveDrom fences with `.wavedrom-host`.
- Invalid/malformed data does not crash Preview runtime helpers.
- PDF readiness selector treats WaveDrom as ready when SVG or `.ms-error` exists.

### Runtime

- Extend `scripts/test/previewRuntimeCheck.js` with one WaveDrom host.
- Verify:
  - Initial render produces SVG or an inline error.
  - `update-body` renders WaveDrom again.
  - Theme switching does not crash WaveDrom.
  - Zoom toolbar still attaches.

### Corpus And Examples

- Add a tracked example, preferably `examples/corpus-wavedrom.md`.
- Add a local ignored corpus case if more adversarial samples are useful.
- Cover:
  - Basic clock.
  - Bus labels.
  - Groups or nested signal entries.
  - Invalid WaveJSON fallback.

## Open Technical Questions

- Does the package accept the JSON5-like WaveJSON syntax used in upstream examples without extra parsing?
- Does WaveDrom output need sanitization, or is generated SVG structurally safe enough under the webview CSP?
- Is eager rendering sufficient for large documents, or should WaveDrom share Mermaid's visible-first behavior?

Resolved:

- Use `wavedrom.renderAny(index, source, wavedrom.waveSkin)` and `wavedrom.onml.stringify(...)`.
- The default skin is exposed through the package root as `waveSkin`; no extra skin import is required.

## Decision

Proceed with webview-side, locally bundled WaveDrom rendering for v0.9. Only fall back to extension-host SVG generation if the package exposes a clean Node API during the spike.
